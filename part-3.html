6 JSON Web Keys

Writing a key down

In part two you generated key pairs and the page showed you a few letters, n, e, x, y. That was a JSON Web Key, and it is the smallest chapter in the handbook because there is genuinely not much to it.

The bank's book of signatures

A bank keeps a book. On every page: a customer's name, a sample of their signature, and a note saying what it may be used for.

The book is not secret. Showing someone a page does not let them forge anything. But without the book, the cashier has nothing to compare against.

A JWK is one page of that book: a key, written as ordinary JSON, so it can be posted, published, fetched and looked up like any other data. A JWK Set is the book, just an object with a keys list in it.

The fields you will actually meet:

The remaining fields are whatever that particular kind of key needs. An elliptic-curve key carries crv, x and y, the curve it lives on, and the coordinates of a point on it. An RSA key carries n and e, the two numbers you will meet properly in the next chapter. And a private key carries d as well, which is precisely the field that must never leave your server.

One field separates public from private Look at the example in the handbook: it has x, y and d. That is a private key. Publish it by accident (and people do) and everything built on it is gone. When you publish a key set, publish keys that have no d in them.

7 JSON Web Algorithms

What is inside the box

Four pieces of machinery hold everything up: an encoding, a hash, a way to mix a secret into that hash, and two kinds of key pair. None of them is beyond you.

7.1  Base64, down to the bit

Beads on a string

Your data is a long string of beads, ones and zeros. Nothing about Base64 changes a single bead.

All it does is decide to read them in groups of six instead of groups of eight, and give every possible group of six a letter. Sixty-four groups are possible, so sixty-four letters are needed. That is the whole name.

Since six is smaller than eight, you end up with more groups than you started with, about a third more. That is why encoded text is always longer than what went in. Nothing was added. It was just cut into smaller pieces.

Three bytes go in as twenty-four bits and come out as four characters. Type below and watch the regrouping happen.

When it does not divide by three Real data rarely comes in neat groups of three bytes. When there is a leftover, zeros are added to fill out the last six-bit group. Ordinary Base64 then pads the result with = signs so the length is a multiple of four. JWTs throw those away, along with swapping + and / for - and _, because the original two are not safe inside a web address. That variant is base64url, and it is what every dot-separated piece you have seen is written in.

7.2  SHA-256, the fingerprint

A fingerprint for anything

Feed it a single word or the whole of an encyclopaedia. Either way, out comes exactly 256 bits, sixty-four characters, no more, no less.

Feed it the same thing twice and you get the same answer twice, always.

Change one letter anywhere, and the answer does not shift a little. It is completely different, as though you had started from something else entirely. And there is no way back: from the fingerprint you cannot rebuild what went in.

That last property has a name, the avalanche effect, and it is easier to be shown than told. Below, the same text twice, with one character changed in the second. Each square is one of the 256 bits; a square lights up when the two fingerprints disagree there.

Roughly half, every time Change one letter or rewrite the whole sentence; it makes no difference, you land near 128. That is exactly what you want. If small changes produced small differences, an attacker could nudge their way towards a match. Because they do not, there is nothing to nudge.

And there is no magic ingredient

SHA-256 looks impenetrable from outside. Inside, it is built from six small functions, and every one of them is just shifting bits sideways and combining them:

function rotr(x, n) { return (x >>> n) | (x << (32 - n)); }

function ch(x, y, z)   { return (x & y) ^ ((~x) & z); }
function maj(x, y, z)  { return (x & y) ^ (x & z) ^ (y & z); }

function bsig0(x) { return rotr(x, 2) ^ rotr(x, 13) ^ rotr(x, 22); }
function bsig1(x) { return rotr(x, 6) ^ rotr(x, 11) ^ rotr(x, 25); }
function ssig0(x) { return rotr(x, 7) ^ rotr(x, 18) ^ (x >>> 3); }
function ssig1(x) { return rotr(x, 17) ^ rotr(x, 19) ^ (x >>> 10); }

That is the entire vocabulary. Rotate, and, or, exclusive-or. The message gets chopped into 512-bit blocks, and those seven functions are run over each block sixty-four times, each round stirring the result of the last. The security comes not from any one clever step but from doing something thoroughly ordinary, sixty-four times, so that every input bit ends up touching every output bit.

Before any of that, the message is padded: a single 1 bit is added to the end, then zeros, then the original length written as a 64-bit number, enough zeros that the whole thing divides neatly into 512-bit blocks. Writing the length in at the end is not decoration; it is what stops two different messages padding out to the same blocks.

7.3  HMAC, and why it wraps twice

You have a hash that nobody can reverse. You have a secret. Mixing them ought to be easy, just hash the secret followed by the message, and you have a code only a secret-holder could produce.

That obvious approach is broken, and the reason is worth knowing.

Signing at the bottom of the page

You write a note and sign at the bottom. Someone takes your note, and without touching a word of it, adds more lines underneath, and produces a new, perfectly valid-looking signature for the longer note, without ever knowing how you sign.

They can do it because of how the hash works: it processes the message in blocks and carries its state forward, so anyone who knows the answer so far can carry on from there.

The fix is to sign the sealed envelope rather than the page inside it. HMAC hashes the message with the key mixed in one way, then hashes that result again with the key mixed in a different way. There is nothing left to append to.

HMAC(m) = H( K′ ⊕ opad ‖ H( K′ ⊕ ipad ‖ m ) ) ipad is the byte 0x36 repeated; opad is 0x5C repeated. ‖ just means "followed by".
K′ is your key padded with zeros to the hash's block size, or hashed down first, if it was longer.

Two constants, two hashes, and that is the whole algorithm. To prove there is nothing hidden, the panel below builds it from those steps by hand and checks the result against your browser's own HMAC.

7.4  RSA, with numbers you can follow

A sum that only works one way

Multiply 61 by 53. Give it a moment and you will get there: 3233.

Now the other direction. Which two numbers multiply to make 3233? Same two numbers, same relationship, and suddenly you are guessing.

Now imagine both numbers are three hundred digits long. The multiplication is still a second's work for a computer. The guessing is not: in 2009 a number of 232 digits was finally taken apart, after two years of work by a cluster of machines. Real keys are far bigger than that.

That gap (easy one way, hopeless the other) is the whole of RSA. Everything else is arithmetic wrapped around it.

The rule at the centre is this:

( me )d ≡ m   (mod n) Raise a number to the power e, then to the power d, and you get back exactly what you started with.
e and n are the public key. d is the private key. Finding d when you only know e and n means factoring n.

7.5  Elliptic curves, drawn

RSA rests on factoring being hard. Elliptic curves rest on a different hard problem, and unlike factoring, this one is genuinely easier to see than to describe.

Start with a curve. Just a shape:

y² = x³ + ax + b
A strange kind of adding

Pick two points on the curve. Draw a straight line through them. That line will cross the curve at exactly one more place. Flip that third point across the horizontal axis, and where you land is called the sum of the first two.

It is not adding as you know it. But it obeys the same rules adding does, and (this is the useful part) the answer is always another point on the same curve. So you can do it again. And again.

And now the hard problem

Hopping is easy. Hop a thousand times and a computer barely notices; there is a shortcut that gets there in about ten steps instead of a thousand.

Now the reverse. Here is where I landed. How many hops did I take?

Nobody knows a fast way to answer that. Not "it takes a while"; there is no known efficient method at all. That question is the elliptic-curve discrete logarithm problem, and it is the entire foundation. Your private key is the number of hops. Your public key is where you landed.

One picture, one correction Real cryptography does not use the smooth curve above. It uses the same equation over a finite field, all arithmetic done modulo a large prime, so every coordinate is a whole number in a fixed range. The curve stops being a curve and becomes a scattering of dots with no shape at all. Every rule still holds; the line through two points wraps around instead of running off. Here is what that actually looks like:
The same curve, as a computer sees it y² = x³ − 2x + 4  (mod 97)

Same equation, same rules, no shape. Notice the mirror symmetry across the middle; that is the same "flip it over the axis" step as before, because if y works then so does −y. This is what your ES256 key is a point on, except that the prime is not 97 but a number with 78 digits.

Why botherA 256-bit elliptic-curve key is about as strong as a 3072-bit RSA key. Twelve times less to store and send, for the same protection.
Why be carefulThe maths only holds for carefully chosen parameters. Elliptic curves have been broken in the wild by implementations that skipped checking their inputs, see chapter 8.
8 Best current practices

Six ways this goes wrong

Almost none of these are flaws in JWTs. They are flaws in how libraries were written and how people used them, which does not make them any less real.

8.1  The one that catches everyone

Two very different things that look identical

A doorman is handed something and told: "check the letter against this."

Sometimes it is a signature sample: compare it, do not copy it. Sometimes it is a rubber stamp, and anyone holding it can also make letters. From across the room, both are just a thing you were handed.

Now let the letter itself say which kind it is.

This is a real attack, and it is elegant enough to be worth walking through.

Your server signs with RS256. Its public key is published; that is the point of a public key. The verify function in your library looks like this:

function jwtDecode(token, secretOrPublicKey) { /* ... */ }

One parameter for both. It makes a sort of sense, a public key is a string, and an HMAC secret is a string.

So the attacker takes your public key, changes the header to "alg": "HS256", and signs a forged token using that public key as the shared secret. Your server passes the same public key in, the library reads alg from the token, decides this is an HMAC token, and checks it against the string it was given. It matches. Of course it matches.

8.2  A secret is not a password

Two very different doors

A password guards a door that fights back. Get it wrong three times and it locks you out, calls someone, makes you wait.

An HMAC secret guards nothing of the kind. An attacker takes your token home and tries guesses on their own machine, as fast as their hardware allows, with nobody watching and no limit. Billions per second.

Which is why the specification is blunt about it: "A key of the same size as the hash output (for instance, 256 bits for HS256) or larger MUST be used." Two hundred and fifty-six bits of real randomness, not a memorable phrase, not your company name with a number after it.

8.3  And four more

1
alg: none
Covered in part one, and still worth naming here. Cut the signature off, relabel the token as unsigned, and hope the reader believes the label.
Fix: the same fix as above, name the algorithms you accept, in your own code.
2
Assuming encryption stops tampering
"If they cannot read it, how could they change it usefully?", by trying, over and over, until a flipped bit lands somewhere that matters. "admin": false is one bit away from something else. An attacker with time and no rate limit can afford to be patient.
Fix: every JWE algorithm carries an authentication tag, which is why this mostly cannot happen. But if you nest tokens, validate every layer, decrypting the outside proves nothing about the signature inside.
3
Invalid curve attacks
Elliptic-curve maths only behaves if the points really are on the curve. Hand a library a "public key" that is not a valid point, and the operations still produce something, something that can be used, step by step, to work backwards to the private key. This has been done to real software.
Fix: check that any public key you are given is a genuine point on the expected curve. Good libraries do this; confirm yours is one of them.
4
Substitution, wrong recipient
A token says only "joe is an admin". It is perfectly signed. But there is a joe at the other service too, and that service shares your signing key. The same token, sent somewhere it was never meant to go, works.
Fix: aud and iss, and check them. A ticket should name its line and its railway.
5
Substitution, right recipient, wrong door
The subtle one. A token for aud: "cool-company/user-database". A second service checks the audience by asking whether it contains "cool-company", and it does. A token meant to write to one database now writes to another.
Fix: compare the audience exactly. "Starts with" and "contains" are not checks; they are near-misses waiting to happen.
✓ The list worth keeping

Eight rules

Every attack in this handbook (all three parts of it) is stopped by something on this list.

Rule 01Name the algorithms yourselfNever let the token choose how it gets checked. This one rule alone kills two of the attacks above.
Rule 02Pick the right algorithm for the situationA shared secret is fine inside one server. It is the wrong answer the moment other parties need to verify. And a token signed with an algorithm your application did not ask for is invalid, even if the maths checks out.
Rule 03Validate every layerA nested token has two sets of rules. Passing the outer one is not passing.
Rule 04Validate cryptographic inputsPublic keys must be real points on the real curve. Numbers must sit in their proper range. Bad inputs do not fail loudly; they leak.
Rule 05Use strong keys256 bits minimum for HS256, from a proper random source. Length without randomness is not strength, a long memorable phrase is still guessable.
Rule 06Check every claim you haveiss, sub, aud, exp, nbf, iat. A valid signature on a token meant for someone else is still a token meant for someone else. Exact matches only.
Rule 07Use typ to tell your tokens apartIf your system issues several kinds, say which is which. It costs nothing and closes a door.
Rule 08Different rules for different tokensSeparate keys per subsystem. Specific issuer names, a URL, not a company name. The more precisely a token describes where it belongs, the less it can be reused somewhere it does not.
And the one the handbook closes on "Don't roll your own crypto." Everything in chapter 7 was shown so you would understand what your library is doing, not so you would write it yourself. The people who wrote those libraries have been broken in public, learned from it, and fixed it. That history is the thing you are actually installing.

Which is the honest note to end on. JWTs look simple, and the simplicity is real, three pieces, two dots, a seal. But every part of this handbook that went wrong went wrong because someone reasonable made a reasonable assumption. Read the header. Name your algorithms. Check your claims. Keep your secrets long and your tokens short-lived.
